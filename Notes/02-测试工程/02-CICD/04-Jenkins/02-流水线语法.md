# 第一课：读懂 Jenkinsfile 的基本结构

先看一个完整的简单示例。这是一个可以作为学习起点的 Declarative Pipeline。

```groovy
pipeline {
    agent any

    stages {
        stage('Checkout') {
            steps {
                echo '开始拉取代码'
            }
        }

        stage('Test') {
            steps {
                echo '开始执行自动化测试'
                sh 'pytest -v'
            }
        }

        stage('Build') {
            steps {
                echo '开始构建镜像'
                sh 'docker build -t my-test:v1 .'
            }
        }
    }

    post {
        success {
            echo '流水线执行成功'
        }
        failure {
            echo '流水线执行失败'
        }
        always {
            echo '流水线执行结束'
        }
    }
}
```

在 Jenkinsfile 中看到的代码，并不全是 Groovy 原生语法，而是 **Groovy 语法 + Jenkins DSL + Shell 命令** 的组合。
`pipeline`、`agent`、`stages`、`stage`、`steps` 并不是普通 Groovy 语句，而是 Jenkins Declarative Pipeline 提供的 DSL（领域专用语言）。
## 核心关键字

| 关键字        | 作用          | 理解方式        |
| ---------- | ----------- | ----------- |
| `pipeline` | 定义整个流水线     | 流水线入口       |
| `agent`    | 指定执行节点      | 在哪里运行       |
| `stages`   | 定义所有阶段      | 阶段集合        |
| `stage`    | 定义单个阶段      | 一个执行环节      |
| `steps`    | 定义具体操作      | 实际执行的命令     |
| `post`     | 定义结束后的处理    | 执行结果回调      |
| `echo`     | 输出日志        | 打印信息        |
| `sh`       | 执行 Shell 命令 | 调用 Linux 命令 |

# groovy基础语法

## 一、Groovy 变量定义

Groovy 中常用 `def` 定义变量。

```groovy
def projectName = 'pytest_jenkins_learn'
def buildNumber = 10
def isEnabled = true

echo projectName
echo "${buildNumber}"
echo "${isEnabled}"
```


Groovy 也支持明确声明变量类型：

```groovy
String projectName = 'pytest'
Integer buildNumber = 10
Boolean enabled = true
```

初学阶段建议优先使用 `def`，减少类型声明带来的负担。

**注意变量作用域。**

```groovy
def project = 'pytest'

pipeline {
    agent any

    stages {
        stage('Test') {
            steps {
                echo "${project}"
            }
        }
    }
}
```

在实际 Jenkins Pipeline 中，Groovy 脚本变量的作用域还会受到 Pipeline CPS 转换和脚本上下文影响。上面这种简单用法可以帮助理解，但复杂场景需要注意变量的定义位置。

## 字符串与插值：String 

这是 Jenkinsfile 中非常常见的语法。
```groovy
def branch = 'main'

echo "当前分支：${branch}"
```

**插值**是 Jenkinsfile 中非常重要的知识点。
Groovy 有两种常见字符串写法：

**1. 单引号字符串**
```groovy
def name = 'Jenkins'
echo 'Hello ${name}'
```
输出：
```text
Hello ${name}
```
单引号字符串不会进行变量插值。

**2. 双引号字符串**
```groovy
def name = 'Jenkins'
echo "Hello ${name}"
```
输出：
```text
Hello Jenkins
```
双引号字符串支持变量插值，这种字符串也叫 GString。

**3. 字符串拼接**
Groovy 还支持使用 `+` 拼接字符串：
```groovy
def project = 'pytest'
def version = '1.0'
def result = project + '-' + version
echo result
```
输出：
```text
pytest-1.0
```

实际开发中，更推荐使用 `${}`，可读性更好。

**4. 三引号字符串**
当 Shell 命令比较多时，可以使用三引号：
```groovy
def project = 'pytest'
sh """
    echo "项目名称：${project}"
    python --version
    pytest -v
"""
```

三引号可以容纳多行内容，非常适合 Jenkins 的 Shell 脚本。
这里还有一个重要细节：Groovy 的三单引号字符串 `'''...'''` 不支持变量插值，而三双引号字符串 `"""..."""` 支持。

## 列表：List
Groovy 使用 `[]` 定义列表。
```groovy
def browsers = ['Chrome', 'Firefox', 'Edge']
// 添加元素
browsers.add('Edge')
// 获取长度
echo "${browsers.size()}"
// 获取元素
echo browsers[0]
// 删除元素
browsers.remove('Firefox')
// 判断元素是否存在
echo browsers.contains('Chrome')
```
 
### 使用 for 遍历 List
```groovy
def browsers = ['Chrome', 'Firefox', 'Edge']

for (browser in browsers) {
    echo "开始执行 ${browser} 测试"
}
```

### each 遍历
Groovy 还有一种更常见的集合遍历写法：
```groovy
def browsers = ['Chrome', 'Firefox', 'Edge']

browsers.each { browser ->
    echo "开始执行 ${browser} 测试"
}
```

这里的 `each` 是集合提供的方法，`{ browser -> ... }` 是闭包。

## 键值对：Map

Map 是 Groovy 中非常重要的数据结构，可以理解为 Python 的字典。
```groovy
def project = [
    name: 'pytest_jenkins_learn',
    language: 'Python',
    framework: 'pytest',
    version: '1.0'
]

// 获取 Map 中的值
echo project.name
echo project['name']

// 修改和添加元素
def project = [
    name: 'pytest',
    version: '1.0'
]
// 修改
project.version = '2.0'
// 添加
project.author = 'Lawwaikit'

echo project.version
echo project.author
```

### each遍历
```groovy
project.each { key, value ->
    echo "${key} : ${value}"
}
```

这里的 `key, value` 是闭包接收的两个参数。

## 循环：for
```groovy
def environments = ['test', 'staging', 'prod']

for (envName in environments) {
    echo "当前环境：${envName}"
}
```
这里的 `in` 表示从集合中依次取出元素。
在 Jenkins Pipeline 中，这类循环可以用来遍历测试环境、浏览器或多个构建配置。

## 条件判断：if / else

Groovy 的条件判断与 Java 类似。
```groovy
def result = 'SUCCESS'

if (result == 'SUCCESS') {
    echo '测试通过'
} else {
    echo '测试失败'
}
```

在 Jenkins Pipeline 中，可以使用它判断当前构建状态：
```groovy
if (currentBuild.currentResult == 'SUCCESS') {
    echo '构建成功'
}
```
注意：`currentBuild` 是 Jenkins Pipeline 提供的对象。

## Groovy 闭包：Closure

这是本节最重要、也最值得理解的知识点。
### 1. 闭包的基本结构
```groovy
def sayHello = {
    echo 'Hello Jenkins'
}

sayHello()
```
可以理解为先定义一个代码块，再通过 `sayHello()` 执行它。

### 2. 带参数的闭包
```groovy
def sayHello = { name ->
    echo "Hello ${name}"
}

sayHello('Jenkins')
sayHello('Groovy')
```

这里的 `name` 就是闭包接收的参数。

### 3. 闭包的隐式参数 it

如果闭包只有一个参数，可以省略参数声明，使用默认参数 `it`：
```groovy
def browsers = ['Chrome', 'Firefox']

browsers.each {
    echo "当前浏览器：${it}"
}
```

这与下面的写法作用相同：
```groovy
browsers.each { browser ->
    echo "当前浏览器：${browser}"
}
```
**记住：** `it` 是 Groovy 闭包中默认提供的单参数名称，不是 Jenkins 专有变量。


# Groovy  与 Jenkins 的环境变量
Jenkinsfile 中最常见的变量操作。尤其是 `env` 和 `params`，它们在实际编写 CI/CD 流水线时几乎必不可少。

## env：获取 Jenkins 构建环境信息

`env` 是 Jenkins Pipeline 提供的环境变量对象，可以获取当前 Job、构建编号、工作空间、Git 分支等信息。

例如：

```groovy
pipeline {
    agent any

    stages {
        stage('查看构建信息') {
            steps {
                script {
                    echo "Job 名称：${env.JOB_NAME}"
                    echo "构建编号：${env.BUILD_NUMBER}"
                    echo "工作空间：${env.WORKSPACE}"
                    echo "构建地址：${env.BUILD_URL}"
                }
            }
        }
    }
}
```

这里有两个需要区分的概念。

`env` 是 Jenkins Pipeline 提供的对象，不是 Groovy 原生语法。`env.JOB_NAME` 等变量则由 Jenkins 在构建过程中提供。

常见环境变量如下：

|变量|含义|
|---|---|
|`env.JOB_NAME`|当前 Job 名称|
|`env.BUILD_NUMBER`|当前构建编号|
|`env.BUILD_ID`|当前构建 ID|
|`env.WORKSPACE`|当前工作空间路径|
|`env.BUILD_URL`|当前构建页面地址|
|`env.JENKINS_URL`|Jenkins 服务地址|
|`env.GIT_BRANCH`|Git 分支信息，取决于 SCM 和插件配置|

**注意：** `env` 中的值通常以字符串形式存在。如果要进行数字比较，需要先转换类型。

```groovy
script {
    def buildNumber = env.BUILD_NUMBER.toInteger()

    if (buildNumber > 10) {
        echo '这是第 10 次之后的构建'
    }
}
```

## Jenkins 环境变量：env
在 Jenkins 中，`env` 是一个内置对象，用来访问当前构建的环境变量。
例如：
```groovy
pipeline {
    agent any
    stages {
        stage('Info') {
            steps {
                echo "Job名称：${env.JOB_NAME}"
                echo "构建编号：${env.BUILD_NUMBER}"
                echo "工作目录：${env.WORKSPACE}"
                echo "构建URL：${env.BUILD_URL}"
            }
        }
    }
}
```

常见内置环境变量：

| 环境变量               | 含义                       |
| ------------------ | ------------------------ |
| `env.JOB_NAME`     | Jenkins 任务名称             |
| `env.BUILD_NUMBER` | 当前构建编号                   |
| `env.BUILD_ID`     | 当前构建 ID                  |
| `env.BUILD_URL`    | 当前构建页面地址                 |
| `env.WORKSPACE`    | 当前工作空间路径                 |
| `env.JENKINS_URL`  | Jenkins 服务地址             |
| `env.GIT_BRANCH`   | Git 分支信息，具体取决于 SCM 插件及配置 |

例如，你之前的 pytest 项目可以这样使用：
```groovy
stage('Test') {
    steps {
        echo "当前工作目录：${env.WORKSPACE}"
        sh 'pytest -v'
    }
}
```

这样就不需要在 Shell 脚本中手动写死项目路径。

## 自定义环境变量：environment

除了 Jenkins 自带的环境变量，你还可以在 Pipeline 中定义自己的环境变量。
```groovy
pipeline {
    agent any

    environment {
        PROJECT_NAME = 'pytest_jenkins_learn'
        TEST_ENV = 'test'
    }

    stages {
        stage('Test') {
            steps {
                echo "项目名称：${env.PROJECT_NAME}"
                echo "测试环境：${env.TEST_ENV}"
                sh 'echo $TEST_ENV'
            }
        }
    }
}
```

这里需要理解两个概念。

`environment` 是 Jenkins Declarative Pipeline 提供的语法，用来声明环境变量。

`env.PROJECT_NAME` 是通过 Jenkins 的 `env` 对象读取环境变量。

另外，`environment` 可以定义在不同作用域：
```groovy
pipeline {
    agent any

    environment {
        GLOBAL_ENV = 'global'
    }

    stages {
        stage('Test') {
            environment {
                LOCAL_ENV = 'test'
            }

            steps {
                sh 'echo $GLOBAL_ENV'
                sh 'echo $LOCAL_ENV'
            }
        }
    }
}
```

其中，全局环境变量在整个 Pipeline 中生效，Stage 级环境变量只在对应 Stage 中生效。

## Jenkins 参数：params

这是另一个非常重要的内置对象。
假设你希望 Jenkins 流水线能够选择不同的测试环境，而不是每次都固定执行 test 环境。
这时可以通过 `parameters` 定义参数，再通过 `params` 获取参数值。

```groovy
pipeline {
    agent any

    parameters {
        choice(
            name: 'TEST_ENV',
            choices: ['test', 'staging', 'prod'],
            description: '请选择测试环境'
        )
		booleanParam(
            name: 'RUN_REGRESSION',
            defaultValue: true,
            description: '是否执行全量回归测试'
        )
    }

    stages {
        stage('Test') {
            steps {
                echo "当前选择的环境：${params.TEST_ENV}"
                sh "pytest --env=${params.TEST_ENV}"、
                echo "是否执行回归：${params.RUN_REGRESSION}"
            }
        }
    }
}
```

当你在 Jenkins 页面点击 Build with Parameters 时，就可以选择测试环境。
![[Pasted image 20261116180500.png]]

这里涉及两个不同的概念：`parameters` 是 Declarative Pipeline 中定义构建参数的语法，`params` 是 Jenkins 提供的参数读取对象。

假设用户在 Jenkins 页面选择 `TEST_ENV=test`，并勾选 `RUN_REGRESSION`，那么流水线就可以根据这两个值决定后续行为。

## currentBuild：当前构建状态

`currentBuild` 是 Jenkins Pipeline 提供的构建对象，主要用于获取和修改当前构建的信息。

例如：

```groovy
pipeline {
    agent any

    stages {
        stage('查看构建状态') {
            steps {
                script {
                    echo "构建编号：${currentBuild.number}"
                    echo "构建结果：${currentBuild.currentResult}"
                    echo "构建持续时间：${currentBuild.duration} ms"
                    echo "构建完整显示名称：${currentBuild.fullDisplayName}"
                }
            }
        }
    }
}
```

常用属性如下：

|属性|含义|
|---|---|
|`currentBuild.number`|构建编号|
|`currentBuild.result`|构建结果，可能为 `SUCCESS`、`FAILURE`、`UNSTABLE` 或 `null`|
|`currentBuild.currentResult`|当前构建结果，通常未结束时也会返回 `SUCCESS` 等状态|
|`currentBuild.duration`|构建持续时间，单位毫秒|
|`currentBuild.fullDisplayName`|构建完整显示名称|
|`currentBuild.description`|构建描述|

这里特别注意 `result` 和 `currentResult` 的区别：构建尚未结束时，`result` 可能是 `null`，而 `currentResult` 通常会返回当前状态，初始值一般是 `SUCCESS`。

### 修改构建结果

除了读取状态，还可以修改构建结果。

```groovy
script {
    currentBuild.result = 'UNSTABLE'
}
```

例如，测试用例存在失败，但你希望流水线继续执行后续报告发布步骤，可以将构建标记为 `UNSTABLE`。

不过，修改构建结果需要谨慎。不要为了让 Jenkins 页面显示绿色就随意覆盖真正的失败状态。

# # **Groovy 流程控制 与 Jenkins 条件执行**

让流水线具备判断和动态执行能力。比如：只有代码来自 `main` 分支时才构建 Docker 镜像，只有用户选择了特定测试环境时才执行对应测试。

## 条件判断：if / else

Groovy 的条件判断与 Java 基本一致。
```groovy
def testEnv = 'staging'

if (testEnv == 'test') {
    echo '执行测试环境用例'
} else if (testEnv == 'staging') {
    echo '执行预发布环境用例'
} else {
    echo '未知环境'
}

这里涉及几个基础运算符：
== 等于 != 不等于 
> < 大于小于
&& || ! 与或非
```

`if/else` 是 Groovy 原生语法，可以在 Jenkins Pipeline 的 `script` 块中使用。
```groovy
stage('Test') {
	steps {
		script {
			def testEnv = 'staging'
			if (testEnv == 'staging') {
				sh 'pytest -v'
			}
		}
	}
}
```
这里的 `script {}` 是 Declarative Pipeline 提供的 Scripted Pipeline 执行入口，允许你在其中使用更自由的 Groovy 脚本。

## Jenkins 条件执行：when

`if/else` 属于 Groovy 原生语法，而 `when` 是 Jenkins Declarative Pipeline 专门提供的条件判断语法。

两者的区别是：`if/else` 可以判断任意 Groovy 表达式，`when` 主要用于决定某个 Stage 是否执行。

### 1. 根据 Git 分支执行 Stage

例如，你希望只有 `main` 分支才执行 Docker 镜像构建：
```groovy
pipeline {
    agent any

    stages {
        stage('Test') {
            steps {
                sh 'pytest -v'
            }
        }

        stage('Build Docker') {
            when {
                branch 'main'
            }

            steps {
                sh 'docker build -t pytest-demo:v1 .'
            }
        }
    }
}
```

执行逻辑是：所有分支都执行 pytest 测试，只有 `main` 分支才执行 Docker 构建。

注意，`branch` 条件通常用于 Multibranch Pipeline。如果你使用的是普通 Pipeline，需要结合实际 SCM 配置获取分支信息。

### 2. 根据构建参数执行 Stage

假设你有一个参数 `BUILD_IMAGE`，希望用户决定是否构建 Docker 镜像。
```groovy
pipeline {
    agent any

    parameters {
        booleanParam(
            name: 'BUILD_IMAGE',
            defaultValue: false,
            description: '是否构建 Docker 镜像'
        )
    }

    stages {
        stage('Test') {
            steps {
                sh 'pytest -v'
            }
        }

        stage('Build') {
            when {
                expression {
                    return params.BUILD_IMAGE
                }
            }

            steps {
                sh 'docker build -t pytest-demo:v1 .'
            }
        }
    }
}
```

这里：
- `booleanParam` 定义一个布尔类型的构建参数。
- `params.BUILD_IMAGE` 获取用户的选择。
- `expression` 用于执行 Groovy 表达式。
- `return` 返回判断结果。

### 3. when 的常见条件

|条件|作用|
|---|---|
|`branch 'main'`|当前分支为 main|
|`environment`|判断环境变量|
|`expression`|执行自定义表达式|
|`not`|对条件取反|
|`allOf`|所有条件都满足|
|`anyOf`|任意一个条件满足|

例如，要求当前是 main 分支，并且用户选择构建镜像：
```groovy
when {
    allOf {
        branch 'main'
        expression {
            return params.BUILD_IMAGE
        }
    }
}
```

这就是多个条件组合判断。

## script：在 Pipeline 中编写 Groovy 脚本

既然 Jenkins 已经有 `when`，为什么还需要 `script`？
因为 Declarative Pipeline 的结构有一定限制。当你需要编写复杂的 Groovy 逻辑时，可以使用 `script`。

例如，动态选择测试环境：
```groovy
pipeline {
    agent any

    parameters {
        choice(
            name: 'TEST_ENV',
            choices: ['test', 'staging'],
            description: '选择测试环境'
        )
    }

    stages {
        stage('Test') {
            steps {
                script {
                    def testConfig = [
                        test: 'http://test.example.com',
                        staging: 'http://staging.example.com'
                    ]

                    def targetUrl = testConfig[params.TEST_ENV]

                    echo "测试目标地址：${targetUrl}"

                    sh "pytest -v --base-url=${targetUrl}"
                }
            }
        }
    }
}
```

这里把前面学习的知识组合起来了：Map 管理环境配置，`params` 获取用户输入，变量保存目标地址，字符串插值将地址传给 Shell。

这就是 Groovy 在 Jenkins Pipeline 中的实际价值。


# Groovy 异常处理与 Jenkins Pipeline 流程控制
## Groovy 异常处理：try / catch / finally

```groovy
try {
    sh 'pytest -v'
} catch (Exception e) {
    echo "测试执行异常：${e.message}"
    throw e  
} finally {
    echo '执行清理操作'
}
```

## Jenkins 专用异常处理：catchError

除了 Groovy 原生的 `try/catch`，Jenkins 还提供了专门的 Pipeline Step：`catchError`。

它的作用是：**捕获某个步骤的失败，让流水线继续执行，同时可以保留失败状态。**
先看一个例子：
```groovy
pipeline {
    agent any
    stages {
        stage('Test') {
            steps {
                catchError(buildResult: 'FAILURE', stageResult: 'FAILURE') {
                    sh 'pytest -v'
                }
            }
        }
        stage('Build') {
            steps {
                echo '继续执行后续阶段'
            }
        }
    }
}
```

假设 pytest 执行失败：
1. Test 阶段被标记为失败。
2. 整个 Build 仍然可以继续执行。
3. Pipeline 最终构建结果仍然是 FAILURE。

**两个参数**
`buildResult`： 整个 Jenkins 构建的结果 
`stageResult`： 当前 Stage 的结果    

它们可以设置为 `SUCCESS`、`UNSTABLE`、`FAILURE` 等结果状态。

**try/catch 和 catchError 如何选择？**

|对比|try/catch|catchError|
|---|---|---|
|类型|Groovy 语法|Jenkins Pipeline Step|
|捕获异常|支持|支持|
|自定义异常处理|灵活|相对简单|
|控制构建结果|需要额外处理|直接提供参数|
|保留 Stage 失败状态|需要额外处理|支持|

我的建议是：需要执行复杂的异常处理逻辑时使用 `try/catch`；希望失败后继续执行其他 Stage，同时保留构建失败状态时，优先考虑 `catchError`。

## Pipeline 重试机制：retry

自动化测试和 Docker 构建有时会遇到临时性错误，例如网络抖动、依赖下载失败。
这种情况下可以使用 `retry`。
### 1. 基本用法
```groovy
pipeline {
    agent any
    stages {
        stage('Install') {
            steps {
                retry(3) {
                    sh 'pip install -r requirements.txt'
                }
            }
        }
    }
}
```

这里的 `retry(3)` 表示最多执行三次。
需要注意：第一次执行也计算在内，因此最多是一次初始执行加两次重试。

### 2. retry 与 try/catch 组合

```groovy
script {
    try {
        retry(3) {
            sh 'pytest -v'
        }
    } catch (Exception e) {
        echo "重试后仍然失败：${e.message}"
        throw e
    }
}
```

这里的执行逻辑是：
pytest 第一次失败 → 自动重试 → 最多执行三次 → 仍然失败则进入 catch → 重新抛出异常。

**工程注意事项：** 不要对所有操作盲目重试。对于数据库写入、发布部署等有副作用的操作，需要先考虑幂等性，避免重复执行造成数据问题。

## Pipeline 超时控制：timeout

如果测试任务出现死循环，或者某个外部服务一直没有响应，流水线可能长时间无法结束。
这时可以使用 `timeout`。
### 1. 基本用法
```groovy
pipeline {
    agent any

    stages {
        stage('Test') {
            steps {
                timeout(time: 10, unit: 'MINUTES') {
                    sh 'pytest -v'
                }
            }
        }
    }
}
```

表示 pytest 最多允许执行 10 分钟。
常见时间单位：
`SECONDS`秒；`MINUTES`：分钟；`HOURS`：小时；`DAYS`：天

### 2. timeout 和 retry 组合

实际项目中，有时既需要重试，又需要限制每次执行时间。

```groovy
pipeline {
    agent any
    stages {
        stage('Test') {
            steps {
                retry(3) {
                    timeout(time: 5, unit: 'MINUTES') {
                        sh 'pytest -v'
                    }
                }
            }
        }
    }
}
```

这里每次尝试最多执行 5 分钟，最多尝试三次。
因此，总执行时间可能接近 15 分钟，此外还需要考虑节点调度和其他步骤的耗时。

## 并行执行：parallel

这是 Jenkins Pipeline 很有价值的能力。
假设你需要执行三个测试任务：
```groovy
sh 'pytest tests/test_login.py'
sh 'pytest tests/test_order.py'
sh 'pytest tests/test_payment.py'
```

默认情况下，它们会按顺序执行。

如果每个测试任务耗时 2 分钟，总耗时大约是 6 分钟。

使用 `parallel` 可以让它们并行执行。

### 1. 基本用法

```groovy
pipeline {
    agent any

    stages {
        stage('Parallel Test') {
            parallel {
                stage('Login Test') {
                    steps {
                        sh 'pytest tests/test_login.py'
                    }
                }

                stage('Order Test') {
                    steps {
                        sh 'pytest tests/test_order.py'
                    }
                }

                stage('Payment Test') {
                    steps {
                        sh 'pytest tests/test_payment.py'
                    }
                }
            }
        }
    }
}
```

三个 Stage 可以同时执行。

### 2. 并行执行的注意事项

并行不意味着一定能加速。
例如，你的 Jenkins 只有一个 Executor，或者多个测试任务都需要占用同一个独占资源，那么并行效果可能有限。
另外，如果多个测试任务同时写入同一个报告文件，也可能产生冲突。建议为不同测试任务指定独立的报告文件，最后再统一收集。

## post：流水线结束后的处理

`post` 可以定义流水线或者 Stage 在不同执行结果下的后续操作。

```groovy
pipeline {
    agent any
    stages {
        stage('Test') {
            steps {
                sh 'pytest -v'
            }
        }
    }
    post {
        always {
            echo '无论结果如何都会执行'
        }
        success {
            echo '流水线成功'
        }
        failure {
            echo '流水线失败'
        }
        unstable {
            echo '流水线不稳定'
        }
        aborted {
            echo '流水线被中止'
        }
        cleanup {
            echo '最后执行清理操作'
        }
    }
}
```


其中，`cleanup` 的执行优先级在其他 post 条件之后。

对于你的 pytest 项目，`post { always { ... } }` 非常重要，因为即使测试失败，也应该尽可能收集测试报告。

例如：
```groovy
post {
    always {
        junit 'reports/*.xml'
    }
}
```


# Groovy 函数与 Jenkins Pipeline 代码复用

前几课我们已经学习了 Groovy 变量、条件判断、循环、集合、异常处理，以及 Jenkins 的 `env`、`params` 和 `currentBuild`。

现在开始学习一个重要主题：**如何把重复的流水线逻辑封装起来，让 Jenkinsfile 更简洁、更容易维护。**

假设你的 pytest 项目逐渐增加了以下流程：安装依赖、执行冒烟测试、执行全量测试、生成报告、构建 Docker 镜像。如果所有逻辑都写在一个 Jenkinsfile 中，文件会越来越长。函数和代码拆分可以解决这个问题。

## 定义 Groovy 函数

Groovy 使用 `def` 定义函数，基本格式如下：

```groovy
def 函数名称(参数) {
    // 函数执行逻辑
    return 返回值
}
```

例如，定义一个简单的问候函数：

```groovy
def sayHello(name) {
    return "Hello, ${name}"
}

def result = sayHello('Jenkins')

println(result)
```

输出：

```text
Hello, Jenkins
```

这里需要理解三个概念：

- `def` 用于定义函数，也可以用于定义变量。
    
- `name` 是函数参数，调用函数时传入实际值。
    
- `return` 用于返回函数执行结果。如果省略 `return`，Groovy 会将最后一个表达式的结果作为返回值。
    

再看一个更贴近自动化测试的例子：

```groovy
def getTestCommand(scope) {
    if (scope == 'smoke') {
        return 'pytest -v -m smoke'
    }

    return 'pytest -v'
}

def command = getTestCommand('smoke')

println(command)
```

输出：

```text
pytest -v -m smoke
```

这样就把测试命令的选择逻辑封装起来了。

## 在 Jenkins Pipeline 中定义函数

Groovy 函数可以在 Declarative Pipeline 外部定义，然后在 `script {}` 中调用。

```groovy
def getTestCommand(scope) {
    if (scope == 'smoke') {
        return 'pytest -v -m smoke'
    }

    return 'pytest -v'
}

pipeline {
    agent any

    parameters {
        choice(
            name: 'TEST_SCOPE',
            choices: ['all', 'smoke'],
            description: '选择测试范围'
        )
    }

    stages {
        stage('执行测试') {
            steps {
                script {
                    def command = getTestCommand(params.TEST_SCOPE)

                    echo "执行命令：${command}"

                    sh command
                }
            }
        }
    }
}
```

这里最重要的是区分 Groovy 函数和 Jenkins Pipeline Step。

`getTestCommand()` 是我们自己定义的 Groovy 函数，而 `echo`、`sh` 是 Jenkins 提供的 Pipeline Step。

**为什么函数调用放在** `script {}` **中？**

因为 Declarative Pipeline 的 `steps` 区域主要用于声明式步骤，复杂的 Groovy 逻辑通常需要放在 `script {}` 中执行。

## 函数可以接收多个参数

实际开发中，一个函数往往需要多个参数。

例如，我们希望根据测试环境和测试范围生成 pytest 命令：

```groovy
def getTestCommand(testEnv, testScope) {
    def command = "pytest -v --env=${testEnv}"

    if (testScope == 'smoke') {
        command += ' -m smoke'
    }

    return command
}

pipeline {
    agent any

    parameters {
        choice(
            name: 'TEST_ENV',
            choices: ['test', 'staging'],
            description: '测试环境'
        )

        choice(
            name: 'TEST_SCOPE',
            choices: ['all', 'smoke'],
            description: '测试范围'
        )
    }

    stages {
        stage('执行测试') {
            steps {
                script {
                    def command = getTestCommand(
                        params.TEST_ENV,
                        params.TEST_SCOPE
                    )

                    echo "测试命令：${command}"
                    sh command
                }
            }
        }
    }
}
```

注意：这里的 `--env` 只是演示命令参数的拼接方式，你的 pytest 项目需要实际实现对应的命令行参数解析逻辑，否则 pytest 会提示参数无法识别。

## 使用 load 拆分 Jenkinsfile

当 Jenkinsfile 越来越复杂时，可以把 Groovy 函数放到独立文件中，再通过 `load` 加载。

例如，项目目录可以设计成这样：
![[Pasted image 20261119144350.png]]

首先，在 `pipelineUtils.groovy` 中定义公共函数：

```groovy
def getTestCommand(scope) {
    if (scope == 'smoke') {
        return 'pytest -v -m smoke'
    }

    return 'pytest -v'
}

def printBuildInfo() {
    echo "当前 Job：${env.JOB_NAME}"
    echo "当前构建编号：${env.BUILD_NUMBER}"
}

// 必须返回 this，供 load 的调用方访问脚本中的方法
return this
```

然后，在 Jenkinsfile 中加载：

```groovy
pipeline {
    agent any
    parameters {
        choice(
            name: 'TEST_SCOPE',
            choices: ['all', 'smoke'],
            description: '测试范围'
        )
    }

    stages {
        stage('初始化') {
            steps {
                script {
                    def utils = load 'pipelineUtils.groovy'

                    utils.printBuildInfo()

                    def command = utils.getTestCommand(
                        params.TEST_SCOPE
                    )

                    echo "测试命令：${command}"
                }
            }
        }

        stage('执行测试') {
            steps {
                script {
                    def utils = load 'pipelineUtils.groovy'
                    sh utils.getTestCommand(params.TEST_SCOPE)
                }
            }
        }
    }
}
```

这里有一个关键点：`load` 会执行指定的 Groovy 脚本，并返回脚本对象。脚本末尾的 `return this` 使调用方能够通过 `utils.getTestCommand()` 访问其中定义的方法。

另外，`load` 使用的是相对于 Jenkins 当前工作空间的路径，因此被加载的文件必须已经通过 SCM Checkout 等方式进入工作空间。

## load 和 Jenkins Shared Library 有什么区别？

当项目只有一个 Jenkinsfile 时，使用 `load` 通常就够了。但当多个项目都需要相同的流水线逻辑时，可以考虑 Jenkins Shared Library。

|对比项|load|Shared Library|
|---|---|---|
|代码位置|当前项目工作空间|独立的 Git 仓库|
|复用范围|通常是当前项目|多个 Jenkins 项目|
|配置成本|较低|需要配置 Jenkins|
|适用场景|拆分单个项目的 Jenkinsfile|多项目统一流水线规范|

Shared Library 通常有这样的目录结构：

```text
jenkins-shared-library/
├── vars/
│   ├── runPytest.groovy
│   └── buildDocker.groovy
└── src/
    └── com/example/
        └── PipelineUtils.groovy
```

其中，`vars/` 目录用于提供可以直接在 Jenkinsfile 中调用的全局步骤，`src/` 目录用于存放常规 Groovy 类和工具代码。

例如，`vars/runPytest.groovy`：

```groovy
def call(String scope = 'all') {
    if (scope == 'smoke') {
        sh 'pytest -v -m smoke'
    } else {
        sh 'pytest -v'
    }
}
```

配置好 Shared Library 后，就可以在 Jenkinsfile 中这样使用：

```groovy
@Library('my-shared-library') _

pipeline {
    agent any

    stages {
        stage('测试') {
            steps {
                script {
                    runPytest('smoke')
                }
            }
        }
    }
}
```

这里的 `runPytest('smoke')` 看起来像普通函数调用，实际上是 Shared Library 暴露出来的自定义 Pipeline 步骤。
